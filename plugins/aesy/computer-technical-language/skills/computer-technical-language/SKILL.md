# 计算机技术用语规范

本规范约束计算机技术领域的术语、措辞、句式和主体表达，适用于技术文档、代码注释、运维说明、故障分析和技术交流，可跨项目独立使用。目标是让读者准确理解技术对象、行为、条件与结果。

说明深度根据材料类型、读者背景和上下文确定。文档结构、格式、维护流程和项目专属命名由各自适用的规范规定。下列示例仅说明表达方法，不规定具体实现。

## 执行方式

- 编写时依据用户提供的事实、项目术语和相关上下文组织表达；润色时先读完整相关段落及必要的相邻定义。按用户指定的材料、语言和范围处理。
- 仅审查时给出问题位置、原因和建议；要求修改时直接修改指定内容。发现事实矛盾或缺少依据时指出具体问题，不以语言润色代替技术决策。
- 完成后核对主体、对象、条件、状态和承诺范围是否与依据一致。关键词搜索只能定位候选问题，不能替代上下文判断；用户要求全文复查时，连续阅读约定范围的正文。
- 规则中的示例用于说明判断方法，不是禁词表。保留有明确技术含义的术语、标识符和原文引述；不要机械替换代码、接口、配置键或项目专名。
- 文档结构、项目命名和维护方式沿用任务所在项目的规范。无需因应用本 skill 新增审批、实现步骤或审查报告。

## 使用标准技术术语

采用所讨论的计算机技术领域公认的术语。需要新概念时，先定义对象、范围与已有概念的区别，避免用词语拼接制造似是而非的概念。

可能影响理解的术语首次出现时，用短定语或括号说明含义；涉及组件时说明其职责。后文无需重复完整定义。

同一概念使用同一名称。服务、模块、进程、实例、接口和数据库分别指明，不能因名称相近而互换。

## 使用具体、自然的技术表达

直接说明主体做什么、操作什么对象、产生什么结果。避免行政公文腔、生硬直译、抽象名词堆叠和夸大能力的隐喻。

| 避免 | 推荐表达 |
| --- | --- |
| 系统级底座、数字化基石 | 按实际形态写核心服务框架、后台管理服务或运行库 |
| 打造中枢神经系统 | 写明实际提供的调度、通信或其他功能 |
| 全生命周期赋能 | 覆盖从创建、运行到销毁的全过程 |
| 本地记录下沉落盘 | 将记录写入本地存储 |
| 处理已闭环 | 写明实际完成的步骤及其结果 |

形象表达只能辅助理解，不能替代实体、职责、条件或执行流程。小标题使用具体机制或所解决的问题，避免口号。

替换措辞须保留原有事实、条件和承诺范围，不能增加验证、审批或执行步骤。例如，材料来源应据实写为用户提供、作者制作或外部引用，不能因润色而改变来源归属。

## 保持概念与技术边界准确

- 实现方式未确定时，说明所需能力和约束；只有依据明确时，才能写成具体机制、产品或技术选型。
- 实例数量须注明约束范围，如进程、主机或集群；“单例”不能直接解释为每台主机只能运行一个实例。
- 数据保护、隐私保护和数据防泄漏分别说明适用范围，不将其中一项直接等同于全部数据保护职责。
- 并发、并行与分布式分别表达，不能仅凭参与者数量推断执行方式或部署范围。
- 权限由代码强制执行时，可用 `code-enforced permission boundaries`；`deterministic` 表达计算确定性，不能代替权限执行机制。
- 配置、策略、知识和提示词的版本化改进，与模型权重训练或强化学习分别表达。
- 请求已发送、对方已接收、执行已完成和结果已保存分别表达，不用同一个“成功”覆盖不同状态。

## 明确主语，精简句段

每句话表达一个主要动作、结论或判定条件。独立动作过多或执行主体变化时拆句，避免用连续的“并且”连接。省略主语或使用“其”“该模块”等指代时，须能从上下文唯一确定所指对象。

一段围绕一个主体或问题展开，逻辑转向时另起一段。句数以表达完整为准，简短注释和答复无需扩展成长段。删除重复铺垫与同义复述，不反复使用“负责”“提供”“实现”等词列出同一职责。

例如，说明请求处理时，可以写：

> 客户端发送请求。服务端校验请求参数，参数无效时返回错误信息。客户端收到错误信息后，向用户显示错误原因。

## 用可观察事实说明能力

描述输入、输出、检查条件、状态变化和失败结果，让读者据此理解能力。避免使用“极致”“颠覆”“无缝”“绝无失败”等没有适用条件与证据的评价。

例如，可写“执行接口发现请求缺少写权限，拒绝该请求并记录原因”，不要只写“系统具有强大的安全能力”。

指标须说明对象、计量方式、测量条件和状态。目标值与测量结果分别表达，没有验证结果时不能写成已经达到目标。组件名称、产品特性名称和效果评价也应分别使用。

## 明确条件、取舍和不确定性

结论须保留适用条件。描述收益与代价时依据已有证据，不用“既要又要”式表达宣称没有成本，不凭空补充资源数值、实现效果或因果关系。

已确认事实与约束使用明确表述；候选方案注明尚未确定；推测注明依据和待验证内容；未知问题写清未知对象。相关性不能直接写成因果关系，资料未说明的能力也不能直接判定为不存在。不要用“后续完善”“进一步优化”等空泛措辞代替具体待定内容。
