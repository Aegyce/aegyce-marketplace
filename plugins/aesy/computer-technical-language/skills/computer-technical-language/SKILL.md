# 计算机技术用语规范

本规范适用于计算机技术文档、架构设计、AI Skill 提示词、代码注释、运维说明、故障分析和技术交流，可跨项目、跨语言使用。通过规范术语、措辞、句式结构与叙述逻辑，使材料既能准确交代动作的执行主体、操作对象、约束条件与执行结果，又便于工程师和 AI 助手直接理解并执行。

说明深度根据材料类型、读者背景和上下文确定。文档结构、格式、维护流程和项目专属命名由各自适用的规范规定。下列示例仅说明表达方法，不规定具体实现。

## 执行方式

- **按人类阅读和执行习惯组织内容**：先交代用途与适用场景，再依次说明交互流程与运行机制，最后写明前置条件、约束边界和异常处理。写给执行者或 AI Agent 的提示词，应直接说明在什么条件下执行什么动作、依据什么判断、得到什么结果。
- **消除电报式断句与机械套话**：避免把完整语义切碎为无连词断句；避免高频滥用“分别……”公式化排比。用顺畅的连接词交代先后顺序和因果关系。
- **拒用抽象造词与内部黑话，统一行业术语**：不用“获准后端”、“受管后端”、“接口契约”、“运行时拓扑”、“载荷”、“终局链”等非标准或项目内部造词。优先使用行业通用概念；面向执行者的文档和提示词不保留内部方案编号或临时设计代号。
- **讲清控制调度与隔离执行的职责分工**：描述多进程或并发系统时，区分轻量的调度协调层与独立隔离的执行进程，不把不同运行角色混为一谈。
- **追求高信息密度，删去啰嗦和“车轱辘话”**：不写连续叠加的防御性否定排比（如“绝不……亦绝不……更绝无可能……”）；不跨章节整段重复同一背景；删去没有信息量的长定语和铺垫套话。
- **按内容选择段落、表格、配图和清单**：原理与取舍用连贯段落；参数对照、状态流转和规则清单用表格；架构分层与边界关系用标准静态配图（如 SVG / PNG）；命令、前提红线和分步操作用清单。
- **决策依据自然附注**：决策代号（如 `[D-002]`）只能作为依据放在句末或括号中，不作句子的语法主语。
- **事实、分级与接口同步核对**：区分“必须阻断的错误”与“仅作提醒的非阻断建议”；改写包含 CLI 命令、参数、字段或状态机的文档时，对照当前真实实现核对一致，不遗留已删除的旧命令。
- **保留专有名词与标识符**：规则中的示例用于说明表达原则，不是机械禁词表。不得误改代码符号、配置键、接口字段、文件命名或已确认的专有名词。

## 1. 按自然认知顺序组织叙述，写清操作与依据

技术文档和提示词面向人类工程师或 AI 执行者，行文按“先意图、后步骤与机制、再边界”组织：

1. **先交代目标与适用场景，再讲流程与边界**：
   - 先说明该模块、工具或指令解决什么问题、什么时候使用；
   - 再说明各组件如何协作，或执行者应按什么顺序调用工具、读取证据、做出判断；
   - 最后写明前置条件、权限与安全边界、失败处理方式。
   - 避免缺乏铺垫就堆砌抽象规则或孤立断言。
2. **决策依据放在句末或括号中，不带入操作指令的主干**：
   - 架构决策代号或参考文档作为依据放在句中或括号里（例如“系统按职责分为控制层和执行层（见决策说明）”）；
   - 不要写“按 D-002，……”或把仅在设计讨论中使用的编号（如 `D6`、`D9`、`D31`）写进操作手册和 Agent 提示词。
3. **写透具体操作，不靠缩略黑话压缩篇幅**：
   - 不要为了表面简短而省掉关键因果或使用自创缩写词；
   - 需要保留的内部状态值或专业术语（如 `rejected`、`unclear`、`advisory`、`gate`），第一次出现时用一句话写清它指什么（例如“初筛（gate，先快速检查 Change 是否值得完整评审）”）。
4. **讲清并发与隔离边界的常见分层**：
   - 描述多进程系统时，不要笼统写成“所有模块在同一进程运行”，应说明各层的实际职责：
     1. **控制调度层**：维护轻量状态机并转发指令，保持事件循环非阻塞；
     2. **共享服务层**：鉴权、审计日志等基础服务独立运行，通过标准进程间通信对外提供能力；
     3. **隔离执行层**：重型任务或不可信脚本在独立的操作系统隔离环境（如独立的子进程、容器或沙箱）中执行，避免影响主调度进程。

## 2. 去掉机械套话，少用“分别……”对仗

“分别”容易掩盖真实的时序、职责归属和隔离方式，导致句子刻板、信息模糊。

| 避免的套路化表达 | 推荐的具体表达 | 改进说明 |
| --- | --- | --- |
| 身份与权限分别检查。 | 鉴权服务先核验调用方的身份凭据；通过后，再对照角色与策略检查其操作权限。 | 写清检查顺序与各自检查的内容。 |
| 各用户的工作状态和数据分别保存。 | 每个用户在各自独立的数据库中保存任务状态与业务数据，避免跨用户互相影响。 | 讲清隔离方式与目的，而不只写“分别”。 |
| 请求受理、执行停止、记录保存和资源释放分别确认。 | 系统按顺序核验每个阶段：先确认请求已入队，再确认底层进程已退出，接着落盘审计日志，最后回收占用的内存与配额。 | 还原真实的操作顺序。 |
| 业务完成与上下文处理进度分别记录。 | 系统在保存任务执行结果的同时，单独记录上下文压缩与更新进度。 | 用正常的并列连接词说明两者独立记录。 |

**规范要求**：
- 区分多个对象或步骤时，直接写出各自的**分工、执行顺序或数据归属**，不在同一段内连续使用“A、B 与 C 分别……”。
- 去掉“……统一维护，……分别保存”这类对仗口头禅。

## 3. 用直白、准确、连贯的语句写提示词与技术说明

好的技术文档和提示词读起来应当像“给新同事交接工作”：主体明确、条件清楚、语流自然。

1. **保持语流连贯，避免电报体**：
   - 不要把本来连贯的一句话切碎成大量没有连接词的短语；
   - 合理使用“先……接着……”、“如果……则……”、“因此”等连词交代先后和因果；
   - 长短句搭配：展开机理时讲透过程，下结论时简明直接。
2. **面向 AI Agent 与操作者的提示词写法**：
   - 直接写“你在什么情况下执行什么动作、读取哪个文件、依据什么条件判断、返回什么结果”；
   - 示例：把“阶段 5 按字段序读取对应载荷完成语义判写并走终局链收口”改为“进入完整评审阶段后，读取待审字段对应的语义规则文件，执行 `decide` 输出结论；如果任务提前结束，按顺序生成报告、询问是否回写并清理临时目录”。
3. **去掉公文腔与空洞比喻**：
   - 不用“系统级底座”、“数字化基石”、“中枢神经系统”、“全生命周期赋能”、“闭环处置”等空话；
   - 改用具体技术描述，如“基础服务框架”、“后台守护进程”、“统一调度器”、“覆盖创建到销毁的完整过程”。
4. **明确动作主体与对象**：
   - 每条操作或规则都写清由谁执行（用户、调度脚本还是评审人员）、对什么对象生效、产生什么结果；
   - 少用长定语修饰抽象名词作主语。

## 4. 采用行业通用术语，拒用生硬抽象造词

优先使用操作系统、编译工具链与分布式工程领域通行的术语。不为了“看起来高级”而拼接晦涩词组。

| 避免使用的造词或黑话 | 推荐使用的通用表达 | 说明 |
| --- | --- | --- |
| 获准后端、受管后端 | **已授权的执行后端**、**系统管理的执行服务** | 明确其服务或进程属性 |
| 资源准入（孤立使用） | **资源配额准入控制**、**CPU/内存配额核验** | 讲清核验什么配额、如何放行或拦截 |
| 接口契约 | **接口规范**、**接口协议**、**接口定义** | 使用工程通行术语 |
| 运行时结构、运行时拓扑 | **进程架构与执行模型**、**服务部署结构** | 讲清进程与服务之间的实际关系 |
| 载荷、终局链、深审草稿（无解释直接使用） | **输入数据 / 规则文件**、**提前结束后的收尾步骤**、**待提交的评审结果** | 对执行者直接说具体对象和步骤 |

**术语一致性要求**：
- 区分服务（Service）、模块（Module）、进程（Process）、实例（Instance）、接口（Interface）与数据表（Table），不在文中混用。
- 没有通行中文译名时保留英文原名（如 `ELF`、`SONAME`、`SRPM`）；同一对象在同一套文档或 Skill 中只使用一个名字，改写时顺带清理旧称呼。

## 5. 删去啰嗦重复与“车轱辘话”

1. **戒除防御性否定排比**：
   - 不要在同一段里连用“绝不……亦绝对不能……更绝无可能……严禁擅自……”。
   - 把正向条件和违规处理写清楚就足够了。例如：“仅在凭证有效且配额充足时放行请求，其余请求直接拒绝并记录日志”；不需要在后面再补三句发誓式否定。
2. **不跨章节整段重复**：
   - 工作原理放在设计/机制章节；验证步骤与预期结果放在测试/验收章节；不在测试或操作步骤里整段复制背景原理。
3. **删去空洞前缀与套话**：
   - 删掉“在系统架构设计上”、“在实际推进过程中”、“在充分核验了底层客观物理证据的前提下”等无意义垫话，直接写动作。
4. **多条件、多维度内容优先整理成表格**：
   - 超过三项的并行属性、状态流转或规则分类，用结构化表格代替长段落堆砌。

## 6. 按内容灵活组合段落、表格、配图与清单

1. **四种常用形式的分工**：
   - **连贯段落**：适合解释设计意图、协作过程、技术取舍；
   - **结构化表格**：适合参数说明、状态流转、规则清单、方案对比；
   - **标准架构图**：适合组件分层、数据流向与隔离边界，优先使用可直接查看的静态矢量 SVG 或高清 PNG，避免在静态或离线 Markdown 阅读器中留下无法渲染的代码块；
   - **要点清单**：适合有序操作步骤、前置检查项与执行命令。
2. **表格保持列义单一、结构完整**：
   - 表头列数与每行单元格数一致；每个单元格只承载一类信息，不把大段未拆分的正文塞进表格。
3. **复杂章节的常用编排**：
   - 先用总览图或一句话交代整体链路，再用段落讲清关键步骤与边界，最后用表格收拢参数、状态或规则明细。

## 7. 保持技术边界清晰与约束分级明确

1. **区分“阻断条件”与“非阻断提示”**：
   - 文档与提示词必须分清哪些条件会**直接阻断流程或判为失败（error / FAIL）**，哪些情况只作为**非阻断的提醒或人工核查建议（advisory / WARN）**；不要把所有注意事项都写成一刀切的阻断禁令。
2. **按方案成熟度如实表述**：
   - 实现方式尚未确定时，只说明需要的能力和约束；已有明确设计或实现依据时，再写出具体机制或选型。
3. **精确写明适用范围**：
   - 实例数量须注明边界（如单线程内、单进程内、单主机内或集群内），不把“单例”含糊当成全集群唯一。
   - 区分并发、并行与分布式；区分代码强制执行的权限边界与计算过程的确定性；区分提示词/配置调整与模型参数训练。
4. **准确区分操作状态**：
   - 明确区分“请求已发送”、“参数已校验”、“排队中”、“执行中”、“执行完成”和“结果已落盘”，不用一个模糊的“成功”覆盖所有中间节点。

## 8. 用可观察事实表述，并核对命令与代码一致性

1. **写可观察的输入、检查与输出**：
   - 通过输入、检查条件、状态变化和报错结果说明能力，不用“极致”、“无缝”、“绝对安全”等空泛修饰词。
2. **对照真实实现核对命令与接口**：
   - 编写或润色包含 CLI 命令、子命令、参数名、配置文件路径或状态机的文档和提示词时，必须核对当前脚本或代码的实际定义；确认已删除的命令、已合并的步骤或更名后的参数必须同步更新，不能只润色文字而保留“幽灵命令”。
3. **指标与来源保留客观事实**：
   - 指标须写明测量对象、条件和统计方式；区分目标值与实测结果，不把尚未验证的指标写成已达成。
   - 保留原有事实、前提条件与代价分析；未确定的参数或后续方案如实标注“待定”或“不覆盖当前未验证场景”，不补造依据。
