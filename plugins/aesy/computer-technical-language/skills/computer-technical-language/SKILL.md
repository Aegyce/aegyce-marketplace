# 计算机技术用语规范

本规范适用于计算机技术文档、架构设计手册、代码注释、运维说明、故障分析和技术交流，可跨项目、跨语言使用。通过规范术语、措辞、句式结构与叙述逻辑，使技术文档既能准确呈现动作的执行主体、操作对象、约束条件与执行结果，又能具备清晰自然的语流、高信息密度和良好的人类可读性。

说明深度根据材料类型、读者背景和上下文确定。文档结构、格式、维护流程和项目专属命名由各自适用的规范规定。下列示例仅说明表达方法，不规定具体实现。

## 执行方式

- **遵循人类认知规律组织行文**：编写与润色时，先交代设计意图与应用场景，再循序展开交互机制与生命周期流程，最后阐明约束条件与边界。避免脱离上下文直接堆砌生硬断言。
- **消除电报式碎片与机械套话**：破除把句子切碎为无连词断句的电报体（Staccato）风格；杜绝高频滥用“分别……”公式化排比。合理运用连接词串联逻辑因果，展现自然流畅的技术语流。
- **拒绝抽象概念造词，采用行业通用规范术语**：坚决摒弃“获准后端”、“受管的底层后端”、“接口契约”、“运行时结构/拓扑”等非标准或过度理论化的生造词；采用“已授权的执行后端”、“接口规范/协议”、“进程架构与执行模型”、“资源配额准入控制”等专业清晰的操作系统概念。
- **框架与运行解耦，讲清并发与实时性机理**：贯彻“框架归框架，运行归运行；控制面极简非阻塞，执行面多进程物理隔离”的最小系统与微内核哲学。清晰区分控制面 Tokio 异步纯非阻塞调度（保障实时性）与执行面多进程物理沙箱抢占（保障并发与隔离）。
- **追求高信息密度，坚决剔除啰嗦冗余与“车轱辘话”**：严禁防御性否定排比（如连续“绝不、亦绝不、更绝无可能”等发誓式赘述）；禁止跨章节镜像重复（机制归机制，验收归验收）；删去空洞的长定语与铺垫套话，精炼技术句式。
- **按内容灵活组合段落、表格、配图与清单等多模态展现**：技术文档切忌单一排版教条。概念叙述与设计哲学使用连贯段落；多维对照、状态流转与参数规范优先使用结构化表格；拓扑结构、物理隔离与通信边界采用高精度架构配图（优先静态矢量 SVG / Retina PNG，杜绝不可渲染的客户端代码块）；前置红线与时序操作使用层级清单。
- **决策依据自然附注**：架构决策代号（如 `[D-002]`）作为设计依据置于叙述之后或括号中，不得作为句子的语法主语。
- **事实与依据优先**：指出逻辑矛盾或信息缺失，不以文字润色代替技术决策；替换措辞时忠实保留原有条件、假设与承诺范围。
- **保留专有名词与标识符**：规则中的示例用于说明表达原则，不是机械禁词表。不得误改接口、配置键、代码符号或已确认的项目专有名词。

## 1. 遵循人类认知规律的叙述层次

技术文档面向人类工程师与架构师，行文组织须遵循“先场景意图、后运行机制、再约束边界”的自然认知规律：

1. **先交代设计意图，再展开交互机制，最后界定约束条件**：
   - 先简明说明该组件、模块或设计所要解决的核心问题与适用场景；
   - 进而阐述各组件之间如何协作，说明数据流与控制流在不同阶段的传递过程；
   - 最后明确前置依赖、资源限制、安全隔离规则与异常降级策略。
   - 避免在缺乏上下文铺垫的情况下直接罗列抽象规则或孤立判定。
2. **决策依据自然融入，不反客为主**：
   - 架构决策代号（如 `[D-002]`）和参考链接作为设计依据，应自然置于阐述之后、句中或括号内作为佐证，例如：“Aegyce 按照系统职责将核心能力划分为五个层次（见决策 [D-002](...)）……”；
   - 不应将决策代号直接用作句子的语法主语（例如避免使用“按 D-002，Aegyce 按以下……”这种生硬八股句式）。
3. **拒绝因过度精简导致的“黑话式晦涩”**：
   - 不为了盲目缩减字数而省略关键机制与因果关联；
   - 涉及数据流转或防护机制时，讲透实际操作过程。例如描述数据脱敏流程时，应直接说明“当请求需要发送给外部大模型时，系统先在本地将敏感数据替换为匿名占位符，并保留映射表；收到响应后再还原真实内容”，避免过度压缩为读者难以理解的词语拼凑。
4. **框架与执行解耦的架构表达（借鉴最小系统与微内核哲学）**：
   - 坚持“框架归框架，运行归运行；控制面极简非阻塞，执行面多进程物理隔离”的设计哲学；
   - 描述并发与实时性时，严禁笼统表述为“所有模块在同一进程运行”，须清晰区分：
     1. **控制面（主协调进程）**：纯轻量状态机推进与信令调度，采用 Rust + Tokio 异步多线程执行器，微秒级非阻塞事件循环，保障高优先级控制信令的实时响应；
     2. **系统服务面**：系统共享服务（如鉴权、记录、沙箱执行）各自采用独立守护进程部署，通过 UDS / gRPC 高效交互；
     3. **执行面**：重型模型推理与外部脚本由 ExecutionService 在 Linux cgroup v2 与命名空间中派生独立隔离沙箱进程执行，由操作系统内核落实物理时间片抢占并发。

## 2. 根治机械套路，破除“分别……”滥用

“分别”常用于表达关注点分离与概念正交性，但机械化、高频套用会导致行文极度刻板，掩盖真实的系统协作机制。

| 避免的套路化表达 | 推荐的机理化表达 | 改进说明 |
| --- | --- | --- |
| 身份与权限分别检查。 | 系统先由 AccessService 验证调用者的身份凭据；核验通过后，再对照所属角色与策略规则校验其具体操作权限。 | 阐明校验先后时序与各自核验内容，替代生硬的“分别检查”。 |
| 各用户的工作状态和数据分别保存。 | 各用户在独立的数据库中维护专属的任务状态与业务数据，避免跨租户相互干扰。 | 讲清隔离载体与隔离目的，而不是只甩一个“分别”。 |
| 请求受理、执行停止、记录保存和资源释放分别确认。 | 流程推进中，系统分步核验每个关键节点：首先确认请求已进入队列，接着确认底层执行已终止，随后落盘持久化审计日志，最后由资源管理器回收占用的内存与计算配额。 | 还原生命周期的具体时序与动作，消除机械排比清单。 |
| 业务完成与上下文处理进度分别记录。 | 系统在保存业务执行结果的同时，单独记录上下文窗口的压缩与更新进度。 | 使用正常的并列或递进连词说明两者的独立记录机制。 |

**规范要求**：
- 区分多个主体或不同流程时，阐述各自具体的**分工、执行阶段或数据归属**，杜绝在同一段落内连续出现公式化的“A、B与C分别XX”。
- 消除“……统一维护，……分别保存”等机械对仗口头禅，用自然的技术用语阐明架构设计原因。

## 3. 使用具体、自然的技术表达与连贯句式

行文应当兼顾专业技术准确性与中文语流的连贯性，消除生硬的电报体（Staccato）风格：

1. **保持语流连贯与自然的呼吸感**：
   - 避免将完整语义生硬切碎为大量毫无连接词的碎句；
   - 合理运用“随后”、“在……之后”、“如果……则”、“从而”、“进而”、“因此”等连词与转折词，串联因果、时序与条件关系，使行文形成自然连贯的逻辑流动；
   - 长短句交织：复杂机制适度展开，结论与断言简明利落。
2. **清除行政公文腔与空洞隐喻**：
   - 彻底摒弃“系统级底座”、“数字化基石”、“中枢神经系统”、“全生命周期赋能”、“闭环处置”等非技术用语；
   - 始终使用计算机领域规范概念，如“核心服务框架”、“后台管理守护进程”、“集中式调度器”、“覆盖从创建到销毁的生命周期全过程”。
3. **明确动作主体与对象**：
   - 直接说明谁执行什么操作、操作什么对象、产生什么结果；
   - 避免过多使用抽象名词作主语的长定语从句；
   - 角色称谓须有明确指代；能直接写出用户、工具或组件时，优先使用具体名称。
4. **保留客观事实与来源**：
   - 替换措辞须保留原有事实、条件和承诺范围，不能增加验证、审批或执行步骤；
   - 材料来源据实写为用户提供、作者制作或外部引用，不能因润色而改变来源归属。

## 4. 采用标准专业术语，拒用生硬抽象造词

优先采用操作系统、分布式系统与 AI 工程领域的行业公认术语。严禁拼接晦涩空泛的非标准词汇，禁止用理论化黑话掩盖具体工程实体。

| 避免使用的抽象造词 / 不自然用语 | 推荐使用的行业规范表达 | 说明与技术内涵 |
| --- | --- | --- |
| 获准后端、受管的底层后端、受管后端 | **已授权的执行后端**、**授权后端服务**、**系统纳管的底层执行引擎** | 明确其作为操作系统独立服务进程或底层沙箱引擎的技术身份 |
| 资源准入（孤立抽象使用） | **资源配额准入控制（Resource Admission Control）**、**资源配额分配与准入核验** | 讲清核验 CPU、内存、显存、Token 配额的具体动作与门槛机制 |
| 接口契约 | **接口规范（Interface Specification）**、**接口协议（Interface Protocol）**、**接口定义** | 采用操作系统与分布式系统通用用语，消除过于抽象的泛理论用词 |
| 运行时结构、运行时拓扑 | **进程架构与执行模型（Process Architecture & Execution Model）**、**进程拓扑结构**、**服务组织架构** | 采用操作系统标准概念，清晰表达进程角色分工与执行载体关系 |

**术语规范要求**：
- 区分服务（Service）、模块（Module）、进程（Process）、实例（Instance）、接口（Interface）与数据表（Table），不能因名称相近而混用。
- 读者可能不熟悉的专用术语首次出现时，通过简要短定语或括号说明其含义与组件职责；随后的正文中保持名称完全一致。

## 5. 追求高信息密度，坚决剔除啰嗦冗余与“车轱辘话”

技术文档应以最高的信息密度传递确凿事实，必须严厉制止以下四类文字通病：

1. **戒除防御性否定排比（拒绝发誓式“车轱辘话”）**：
   - 严禁在同一段落内连续使用“绝不……、亦绝对不能……、更绝无可能……、绝对无法作为借口……、严禁擅自……、坚决杜绝……”等高情绪强度的重叠排比句。
   - 规则与约束陈述一次即具备充分效力。正向讲清准入条件即可自然涵盖否定边界（例如：“仅当身份凭证有效且配额充足时放行调用，其余请求直接拦截并记录审计日志”；无需再追加三句“绝不因为系统繁忙而放宽、绝不借口网络延迟而越权、更绝对不能将未决视为成功”）。
2. **拒绝跨章节镜像重复（机制归机制，验收归验收）**：
   - 架构章节阐述系统如何工作与交互原理；验收章节专门聚焦于验证方法、输入用例、预期产物与判定准则。
   - 严禁在测试验收、功能清单或附录等章节中，把前文的设计原理、生命周期流转、安全防护背景整段整篇地复制重写一遍。
3. **剔除空洞的长定语与铺垫套话**：
   - 删去“在系统架构设计上”、“在实际推进过程中”、“在底层操作系统层面”、“在充分核验了底层客观物理证据的前提之下”等毫无信息增量的前缀，直接展开技术动作。
4. **精炼技术句式，提升单位字数价值**：
   - 凡是一句话能阐明因果关系的，绝不用三重复合从句反复绕弯；
   - 凡是有多项并行属性、流程阶段或对比维度的，优先以结构化表格呈现，坚决压缩晦涩拖沓的长篇叙述。

## 6. 展现形式灵活组合规范（段落、表格、配图与清单）

技术文档切忌通篇单一排版形式（通篇密不透风的纯文字墙、或通篇无背景解释的孤立表格、或依赖不可渲染客户端脚本的代码图）。应根据具体内容特征与读者认知需求，灵活、有机地组合**自然段落、结构化表格、专业架构配图与清晰要点清单**：

1. **各类展现形态的核心职责与适用边界**：
   - **自然段落（叙述与机理）**：最适合交代设计意图、背景痛点、协作机理、技术权衡与深层哲学依据；
   - **结构化表格（多维矩阵与规范）**：最适合多维度属性对照、生命周期状态转移、API / 接口参数定义、异常升级矩阵、配置项清单及角色权限矩阵；具有极高信息密度与视线扫描效率；
   - **专业架构配图（拓扑与空间流动）**：最适合全局架构分层、进程承载拓扑、网络与沙箱边界、跨系统与多主体数据流图；遵循 Claude / Anthropic 克制风格，并优先采用标准静态图像（高精矢量 SVG / 高分 Retina PNG），杜绝在离线或静态文档系统（如 Docsify / 离线 Markdown）中产生未经编译渲染的代码块；
   - **层级与流程清单（有序步骤与条件）**：最适合严格时序步骤、前置依赖清单、操作红线与部署验证命令。
2. **表格结构完整对称与语义闭环**：
   - 表头列数必须与每一行数据单元格数量严格一致；各列具有明确的语义定义，避免将多重属性杂糅在同一个单元格中；
   - 单元格内容应为语义完整的短语或要点，避免无主谓的碎片词组堆积，也不可将未分段的大篇幅叙述直接塞入表格。
3. **图文表融合的组合实践模式**：
   - 复杂章节建议遵循“**总览配图建立全局心智模型 → 核心段落剖析运行逻辑与时序机理 → 结构化表格收敛关键规则/参数/状态矩阵 → 要点清单锁定操作红线**”的复合编排范式，确保读者既能在宏观上建立清晰架构印象，又能在微观上精准查阅参数与判定标准。

## 7. 保持概念与技术边界准确

1. **方案成熟度分级表述**：
   - 实现方式未确定时，说明所需能力与约束；只有依据明确时，才能写成具体机制、产品或技术选型。
2. **精确界定约束范围**：
   - 实例数量须注明约束范围（如单线程内、单进程内、单主机内或集群内）；“单例”不能直接解释为每台主机只能运行一个实例。
   - 数据保护、隐私保护和数据防泄漏分别说明适用范围，不将其中一项直接等同于全部数据保护职责。
   - 并发、并行与分布式分别表达，不能仅凭参与者数量推断执行方式或部署范围。
   - 权限由代码强制执行时使用 `code-enforced permission boundaries`；`deterministic` 表达计算确定性，不能代替权限执行机制。
   - 配置、策略、知识和提示词的版本化改进，与模型权重训练或强化学习严格区分。
3. **区分状态与生命周期节点**：
   - 明确区分操作的各个生命周期阶段：“请求已发送”、“对方已接收”、“参数已校验”、“排队就绪”、“正在执行”、“执行完成”与“结果已持久化”，不能用单一的“成功”覆盖不同状态。

## 8. 用可观察事实说明能力与明确不确定性

1. **描述可观察的输入与输出**：
   - 描述输入、输出、检查条件、状态变化和失败结果，让读者据此理解系统能力；
   - 避免使用“极致”、“颠覆”、“无缝”、“绝无失败”等没有适用条件与客观证据的修饰词。例如，写“执行接口检测到请求缺少写权限，拒绝该请求并记录审计日志”，不要只写“系统具有强大的安全能力”。
2. **指标客观完整**：
   - 指标须说明测量对象、计量方式、测量条件和系统状态；
   - 目标值与实测结果严格区分，未经验证时不能写成已经达到目标。
3. **保留前提条件与权衡分析**：
   - 技术结论须保留适用条件；描述收益与代价时依据已有工程事实与证据，不用“既要又要”式表达宣称没有系统开销，不凭空补充资源数值、实现效果或因果关系。
4. **区分既定事实、待定项与推测**：
   - 明确区分已确认方案与候选方案、系统自身职责与外部依赖能力；
   - 未确定参数或方案统一标注为“待定”或“留作后续演进”，不伪造确定性。
